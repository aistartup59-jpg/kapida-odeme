# ADR-014: Open Provider Registry

- **Status:** Accepted
- **Date:** 2026-07-31
- **Extends:** ADR-007

## Context

ADR-007 requires that adding a payment provider cost one adapter plus its registration, with no business logic change. In practice it cost more than that. `ProviderType` was a closed enum listing four named providers, and `merchant_payment_providers.providerType` was a Postgres enum built from it. Onboarding a provider therefore meant editing the enum, writing a schema migration, and deploying both — before the adapter could be used at all. Worse, the enum listed providers that had no adapter, so a merchant could configure `IYZICO` and only discover at payment time that nothing was installed.

The provider set is open by nature: iyzico, PayTR, ParamPOS, Sipay, or a bank's own gateway, chosen per merchant.

## Decision

A payment provider is identified by a free-form string id (`ProviderId`), never an enum.

`ProviderRegistry` is the single source of truth for which providers exist. An adapter registers itself under its own id, declared alongside the adapter (for example `PARAM_POS_PROVIDER_ID` in `parampos.adapter.ts`), not in a shared enum.

Everything downstream asks the registry rather than a hardcoded list:

- Merchant configuration validates `providerType` with `registry.has(id)`, and reports `registry.list()` when rejecting.
- `PaymentProviderFactory` resolves through the registry.
- `merchant_payment_providers.providerType` is a text column, so installing a provider never requires a schema migration.

Ids are normalized (trimmed, upper-cased) before they are matched or persisted, so `param_pos` and `PARAM_POS` cannot fork one merchant's configuration into two rows.

Adding a provider is therefore: write the adapter, register it. Nothing else changes.

## Consequences

- A provider with no installed adapter is rejected at configuration time with a message naming what is installed, instead of failing later at dispatch.
- No enum, no DB type, and no migration stands between a finished adapter and a merchant using it.
- The database no longer constrains the provider vocabulary. That constraint moves to the registry, which is the only component that actually knows what is installed.
- Rolling the schema back to the closed enum only succeeds while every stored value is one of the four it originally held.

## Alternatives Considered

- Keeping the enum and adding values as providers are onboarded: rejected because it makes every provider a schema change, and keeps advertising providers that are not installed.
- Accepting any string without checking the registry: rejected because a typo would be stored happily and only surface as a failed payment.
